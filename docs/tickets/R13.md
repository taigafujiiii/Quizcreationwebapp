# R13: E2E修復（条件付き）

## 目的

進め方ステップ5冒頭の既存E2E動作確認で `npm run test:e2e` が失敗した場合にのみ発動し、失敗の切り分けと修復（`.env.e2e` 整備・前提URL・現仕様との乖離テスト）を行う。**発動しない（全green）なら本チケットはクローズ**。

## 発動条件

- ステップ5冒頭で `npm run test:e2e` を実行し、**1件以上 fail**（skip は fail ではない）。
- fail が「テスト側の前提ずれ」か「実装のリグレッション」かを切り分け、前者はテスト修正/環境整備、後者は該当実装チケットへ差し戻す。

## 対象ファイル（発動時のみ）

- `.env`（`test:e2e` スクリプトが `source .env` するため。下記備考）/ `.env.e2e`（テンプレは `.env.e2e.example`）
- `playwright.config.ts`（baseURL / webServer 設定）
- `tests/e2e/*.spec.ts`（現仕様と乖離したテストの修正・skip）

## 事前調査（判明済みの想定失敗モード）

### 1. 必須環境変数（テスト実体から抽出）

`test:e2e` は `set -a; source .env; set +a; npx playwright test`。**`.env` を読む**（`.env.e2e` ではない）点に注意。`.env.e2e.example` は本環境の権限設定で直接読めなかったため、実テストコードから必要変数を列挙する:

| 変数 | 使用テスト | 必須度 |
|------|-----------|--------|
| `VITE_SUPABASE_URL` | admin-api-auth, admin-invite-user, invite-rate-limit, functions-routes, register-api | API系で必須（未設定は即fail） |
| `VITE_SUPABASE_ANON_KEY` | 同上 | 同上 |
| `E2E_ADMIN_EMAIL` / `E2E_ADMIN_PASSWORD` | admin.spec, admin-api-auth, admin-invite-user, invite-rate-limit, register-api(dup test) | admin系で必須 |
| `E2E_USER_EMAIL` / `E2E_USER_PASSWORD` | user.spec | user系で必須 |
| `E2E_BASE_URL` | playwright.config.ts:3（未設定時 `https://quiz-app-alpha-umber.vercel.app`） | 任意（既定=本番） |
| `E2E_BROWSER` / `E2E_USE_CHROME` / `E2E_HEADFUL` 等 | playwright.config.ts:4-12 | 任意 |

- 未設定時: `admin.spec.ts` / `user.spec.ts` は `ensureEnv()` で **throw**（ハードfail）。`admin-api-auth` 等は `expect(...).toBeTruthy()` で fail。
- `register-api.spec.ts` は `isSupabaseReachable()` で **到達不可時 `test.skip`**（graceful）。`admin-api-auth` / `admin-invite-user` / `invite-rate-limit` にはこのガードが無く、Supabase 不達・認証失敗で**ハードfail**する。

### 2. baseURL 前提（本番URL依存）とローカル/CIでの成立条件

- 既定 baseURL は**本番 Vercel URL**。`smoke.spec.ts` / `admin.spec.ts` / `user.spec.ts` は baseURL（＝本番）に対して走る。**本番デプロイが現行コードと一致していないと、R08〜R11 の変更は本番未反映のため意味を持たない**。ローカル検証したい場合は `E2E_BASE_URL=http://localhost:5173` を設定し、別途 `npm run dev` を起動（`playwright.config.ts` に `webServer` は未設定＝自動起動しない）。
- **`register-page.spec.ts` は baseURL を無視して `LOCAL_BASE=http://localhost:5173` にハードコード**でアクセスし、Supabase 呼び出しを route mock する。したがって**このファイルだけは常にローカル dev サーバ(5173)起動が前提**。dev サーバ未起動なら `net::ERR_CONNECTION_REFUSED` で全fail。
- CI で走らせる場合: (a) API系は `VITE_SUPABASE_*` + `E2E_*` creds、(b) register-page 用に dev サーバ、(c) baseURL 系は到達可能なデプロイ URL、の3系統が要る。

### 3. 現仕様と乖離しているテスト（**重要・ルート変更起因**）

`App.tsx` は `/register` `/accept-invite` `/reset-password` `/verify` を**Route登録していない**（`*` キャッチオール → `/` → `StudentRoute` → `/select-company`）。一方コンポーネント（`Register.tsx` / `AcceptInvite.tsx` / `ResetPassword.tsx` / `Verify.tsx`）は実在。これにより次のテストは**現状ほぼ確実に fail** する:

- **`register-page.spec.ts`（全11ケース）**: `/register` へ goto しても `/select-company` にリダイレクトされ、`toHaveURL(/\/register$/)`・見出し「アカウント登録」・入力欄（姓/名/メール/所属会社）が取れない。`/login` の「登録申請」リンク（`Login.tsx:180` に実在）をクリックしても遷移先 `/register` が未登録のため URL 判定 fail。
- **`accept-invite-invalid.spec.ts`**: `/accept-invite#` へ goto しても未登録 → リダイレクトし、見出し「この招待リンクは使用できません」が出ず fail。

これは DESIGN.md が言う「Register/Verify等のルート変更」／S11「Verify.tsx（ルート未登録）」と一致する既知乖離。**テストの前提（これらのルートが存在する）が現実装と食い違っている**。

### 4. その他の想定挙動

- `invite-rate-limit.spec.ts`: 2回目が 429 でなければ `test.skip`（invite_logs 未整備環境を許容）。R09 でレート制限を拡張しても invite の挙動は不変のため回帰しない想定。
- `functions-routes.spec.ts` / `admin-api-auth.spec.ts` / `admin-invite-user.spec.ts`: `/functions/v1/server/...` の実ルートを叩く。R08〜R10 の `server/index.ts` 変更が**デプロイ済み**であることが前提（未デプロイだと旧挙動でfail/passがぶれる）。

## 修復方針（発動時）

fail の原因別に:

1. **env/creds 欠落** → `.env`（`test:e2e` が読むファイル）に必須変数を投入。テンプレは `.env.e2e.example`。SPEC §11「`.env.e2e` はローカル用・本番認証情報をファイル共有しない」に従い、値の所在はオーナーに確認（MEMORYの方針）。**スクリプトが `.env` を source する一方テンプレ名が `.env.e2e.example` である不整合**も是正（スクリプトを `.env.e2e` 参照に変えるか、`.env` に集約するかをオーナー確認）。
2. **register-page が接続不可** → `npm run dev`（5173）を起動して実行、または `playwright.config.ts` に `webServer: { command: 'npm run dev', url: 'http://localhost:5173', reuseExistingServer: true }` を追加（register-page 専用の前提を自動化）。
3. **ルート未登録起因の乖離（§3）** → 二択をオーナー判断:
   - (a) **ルートを整備**（`/register` `/accept-invite` `/reset-password` を `App.tsx` に登録。R11 備考と同根の課題）→ テストが仕様どおり通る。受講生PIN方式へ移行後もこれらフロー（招待受諾・パスワード再設定・自己登録）を提供するなら本筋の修正。
   - (b) **テストを現仕様に合わせて更新/skip**（ルートを廃止する意思決定なら、`register-page.spec.ts` / `accept-invite-invalid.spec.ts` を現行フローに書き換え or `test.skip` + 理由コメント）。
   - **勝手にどちらかへ倒さず、オーナーに「これらの認証フローを現行UIで提供するか」を確認してから修復**（事業モデル＝受講生PIN方式への移行判断に直結するため）。
4. **実装リグレッション** → 該当実装チケット（R08〜R11 等）へ差し戻し。テスト側は変更しない。

## 完了条件（発動時）

- `npm run test:e2e` が green（環境都合の `test.skip` は許容し、理由が明示されていること）。
- ルート未登録起因の乖離テストについて、(a) ルート整備で pass か (b) 現仕様に合わせた更新/skip か、**オーナー判断に基づき**決着している（勝手な倒し込みが無い）。
- `.env` / `.env.e2e` の変数不整合（スクリプトの source 対象）が解消。

## 実行するテストコマンド

```bash
# 発動判定（step5冒頭）
npm run test:e2e

# 切り分け例（ローカル・register-page のみ、dev起動下で）
npm run dev &           # 5173
npm run test:e2e -- register-page.spec.ts

# API系のみ（creds + Supabase到達必要）
npm run test:e2e -- admin-api-auth.spec.ts admin-invite-user.spec.ts functions-routes.spec.ts

# baseがローカルの場合
E2E_BASE_URL=http://localhost:5173 npm run test:e2e -- smoke.spec.ts user.spec.ts admin.spec.ts
```

## 依存・並列

- 依存: **`.env.e2e`（認証情報）の提供**（オーナー）。条件付き発動。
- ルート整備を選ぶ場合は R11 / App.tsx 変更（R04）と衝突しうるため、その調整が必要。
- ブランチ: `feature/R13`、単独PR（発動時のみ）。

## 備考

- **`.env.e2e.example` は本作業環境の権限設定で直接読めなかった**（`.env*` へのアクセスが拒否）。上記「必須環境変数」はテストコード（`process.env.*` 参照箇所）と `playwright.config.ts` から確定した実体ベースのリスト。`.env.e2e.example` に追加の任意変数が定義されている可能性があるため、発動時に実ファイルを参照して差分確認すること。
- **診断で判明済みの「Register/Verify等のルート変更」は E2E の前提と食い違う**（§3）。`register-page.spec.ts` と `accept-invite-invalid.spec.ts` が現行 `App.tsx` のルーティングと矛盾しており、R13 発動時の主要因になる可能性が高い。これは R11・R12 の「要確認（ルート未登録）」と同一の根本課題であり、3チケットで一貫した判断が要る。
- `test:e2e` は `set -a; source .env` に依存するため、`.env` 不在だとスクリプト自体が（source で）警告/失敗しうる。CI では env 注入方式（`.env` 生成 or 直接 export）を要検討。
