### B. docs/DESIGN_S1_pin_scope.md（S1対策設計書・実装しない）

PINスコープトークン方式の設計を記述する。骨子:

1. **背景・問題（S1）**: 公開エンドポイントが service role で RLS をバイパスし、`allowed_unit_ids` の照合が**フロントのみ**（`QuizSetup.tsx` / `App.tsx`）。API直叩きで PIN 未入力のまま他社ライセンス単元の問題・正解を全取得可能。会社別ライセンス制御が実質無効（根拠: `server/index.ts:170-240`）。
2. **方式概要**: `verify-pin` 成功時に**短命の署名付きスコープトークン**を発行し、以降の `/public/quiz-data` `/public/unit-categories/:unitId` `/public/questions` でトークンを検証、トークンに埋め込んだ `companyId` / `allowedUnitIds` と要求単元・カテゴリを**サーバ側で照合**する。
3. **トークン仕様**:
   - 形式: JWT（HS256、Edge Function の共有秘密 `PIN_SCOPE_SECRET` で署名）または Supabase の JWT 秘密で署名。ペイロード: `{ companyId, allowedUnitIds, iat, exp }`。
   - 有効期限: 短命（例 30〜60分）。学習セッションを跨ぐ場合は再入力 or リフレッシュ方針を検討。
   - 受け渡し: レスポンスボディで返し、フロントは（localStorage or メモリ）保持。以降のリクエストは `Authorization: Bearer <scopeToken>` あるいは専用ヘッダ `x-pin-scope`。
4. **サーバ側検証（照合ロジック）**:
   - `/public/questions`: 要求 `categoryId(s)`/`unitId` を解決し、対応する `unit_id` が全て `token.allowedUnitIds` に含まれることを検証。含まれない要求は 403。
   - `/public/unit-categories/:unitId`: `unitId ∈ allowedUnitIds` を検証。
   - `/public/quiz-data`: 返却 units/categories を `allowedUnitIds` でフィルタ（または要トークン化）。
   - トークン無効/期限切れ → 401、スコープ外 → 403。
5. **フロント改修範囲（実装時）**: `SelectCompany`（PIN検証でトークン受領・保存）、`publicApi`（`adminApi.ts` の各 `publicFetch` にトークン付与）、`Quiz.tsx` / `QuizSetup.tsx` / `CategoryList.tsx`（トークン前提のデータ取得）。CompanyContext にトークンを保持。
6. **移行・後方互換**: 段階導入案（トークン任意期間 → 必須化）。トークン未提供時の挙動（当面は従来どおり許可し警告ログ → 後日 deny）。
7. **代替案比較**: (i) PINスコープトークン（推奨・ステートレス・失効はexp依存）、(ii) サーバ側セッション（Redis/テーブルにPIN検証状態を保持・失効容易だがインフラ増）、(iii) 受講生も匿名 Supabase セッション化（RLSに寄せる・大改修）。トレードオフを表で提示し推奨を明示。
8. **非スコープ/申し送り**: PIN のハッシュ化（R09備考）との関係、レート制限（R09）との併用。実装は別スケジュール。
