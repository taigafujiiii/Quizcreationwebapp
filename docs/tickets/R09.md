# R09: S3 PIN保護強化（PIN UNIQUE制約 + verify-pin/register-request レート制限 / S6同梱）

## 目的

会社PIN（`companies.pin`）が「平文保存・UNIQUE制約なし・レート制限なし」（DESIGN.md S3）で、次の失敗シナリオがある。

- 重複PINを設定すると `verify-pin` の `.eq('pin', pin).maybeSingle()`（`server/index.ts:154-158`）が複数ヒットしエラー化 → 該当両社ともログイン不能。
- `/public/verify-pin`（148行）に試行レート制限がなくPIN総当たりが可能。
- `/public/register-request`（243行）にレート制限がなく、かつ毎回 `listUsers({perPage:1000})`（270行）を実行 → 招待メール爆撃・プロバイダクォータ枯渇（S6）。

本チケットで (a) PIN の partial UNIQUE 制約、(b) `verify-pin` / `register-request` へのレート制限（`/admin/invite` の `invite_logs` 方式＝`server/index.ts:553-598` のパターン踏襲）を追加する。

## 対象ファイル

- 新規 migration: `supabase/migrations/<R08より後のタイムスタンプ>_company_pin_unique.sql`（例 `20260731000000_company_pin_unique.sql`。R08の migration より後にソートされること）
- `supabase/functions/server/index.ts`（`/public/verify-pin` 148-167行、`/public/register-request` 243-319行）

## 実装手順

### A. 重複PIN事前確認（migrationより先に必ず実行）

partial UNIQUE index は既存に重複PINがあると**作成に失敗**する。migration 適用前に、検証・本番の両DBに対し次を Supabase SQL Editor で実行する。

```sql
select pin, count(*) as n
from public.companies
where pin is not null
group by pin
having count(*) > 1
order by n desc;
```

- 0件 → Bへ進む。
- **1件以上ヒットした場合は、勝手にPINを変更・NULL化しない。オーナーに重複会社の一覧を報告し、どちらのPINを変更するか指示を仰ぐ**（会社ログインに直結する運用データのため。バックアップ方針=MEMORY「上書き前バックアップ必須」に従い、変更する場合も現行値を控えてから）。重複解消後にBを適用する。

### B. PIN partial UNIQUE制約（migration）

NULL を許容しつつ、非NULLのPINは一意にする。

```sql
create unique index if not exists companies_pin_unique
  on public.companies (pin)
  where pin is not null;
```

### C. レート制限用ログテーブル（migration・同一ファイル）

`invite_logs` は `inviter_id NOT NULL` / `invitee_role in ('user','admin')` の制約があり、認証なしのPIN試行・登録申請には**スキーマが適合しない**。そこで `invite_logs` と同型の専用テーブルを新設する（invite_logs方式＝window内カウント＋テーブル不在時graceful skip、のパターンを踏襲）。

```sql
create table if not exists public.public_action_logs (
  id uuid primary key default gen_random_uuid(),
  action text not null,          -- 'verify_pin' | 'register_request'
  ip text not null default '',
  email text,                    -- register_request のみ
  status text not null,          -- 'attempt' | 'blocked_rate_limit' | 'failed' | 'ok'
  meta jsonb not null default '{}'::jsonb,
  created_at timestamptz not null default now()
);

create index if not exists public_action_logs_action_ip_created_idx
  on public.public_action_logs (action, ip, created_at desc);
create index if not exists public_action_logs_action_email_created_idx
  on public.public_action_logs (action, email, created_at desc);

alter table public.public_action_logs enable row level security;
-- service role のみ書込（Edge Function経由）。認証ユーザー向けポリシーは付与しない。
```

### D. verify-pin レート制限（Edge Function）

`server/index.ts:148-167` の `verify-pin` 冒頭で、クライアントIP（`c.req.header('x-forwarded-for')?.split(',')[0]?.trim()` を第一候補、無ければ `x-real-ip`）をキーに window カウント。`invite/553-598` と同型に:

- 定数例: `windowMinutes=10`, `maxPerIpPerWindow=10`。
- `public_action_logs` を `action='verify_pin' and ip=<ip> and created_at >= sinceIso` で count。
- count クエリが「テーブル不在」エラー → `skipRateLimit=true`（graceful degradation。デプロイ順で migration 未適用でもログインを壊さない）。
- 上限到達 → `status='blocked_rate_limit'` を insert して `429`（`'PIN試行が多すぎます。しばらく待って再試行してください'`）。
- 通過時は判定後に `status='ok'`/`'failed'` を1件 insert（失敗回数もカウント対象に含めるため attempt を先行 insert する方式でも可。invite の attempt→更新パターンに合わせる）。

PIN照合本体（`.eq('pin', pin).maybeSingle()`）は据え置き（B適用後は複数ヒットが構造的に発生しない）。

### E. register-request レート制限 + listUsers最適化（Edge Function）

`server/index.ts:243-319`:

- レート制限（S6）: `action='register_request'` で **email 単位**（`maxPerEmailPerWindow=1` 相当、invite の invitee 側と同思想）と **IP単位**（`maxPerIpPerWindow` 例: 5/10分）の二軸で window カウント → 超過は `429`。テーブル不在時は skip。
- `listUsers({perPage:1000})`（270行）の毎回実行は招待爆撃時に高コスト。**レート制限を通過した後にのみ**既存ユーザー確認を行う順序にする（現状の重複チェック自体のロジックは維持し、実行を制限通過後に移すだけ）。※listUsers のページング根本改善はスコープ外（S6の主対策はレート制限）。

## 完了条件

- 同一PINを2社に設定しようとすると DB制約違反（`PATCH /admin/companies/:id` で 500 相当のUNIQUEエラー）になり、重複が構造的に発生しない。
- `verify-pin` を短時間に上限超で叩くと `429` が返る。正常系（1回の正しいPIN入力）は従来どおり `allowedUnitIds` を返す。
- `register-request` を同一メール/同一IPで連打すると `429` が返り、招待メールが再送されない。正常系（初回・妥当データ）は従来どおり `success:true`。
- `public_action_logs` 未適用の状態でも verify-pin / register-request が 500 で落ちない（graceful skip）。
- 既存データ変更なし（PIN値は触らない）。UNIQUE index は重複解消後にのみ適用。

## 備考

- **maybeSingle複数ヒット問題（S3）は B の partial UNIQUE 制約で構造的に解消される**（`verify-pin` の `.maybeSingle()` はもう複数行を受け取らない）。
- **要確認（IP取得）**: Supabase Edge Functions（Deno.serve）で `x-forwarded-for` が期待どおり実クライアントIPを含むか、環境で検証が必要。含まれない/プロキシ集約される場合、IP単位の制限が緩くなるため email 単位（register-request）を主・IPを従とする。verify-pin は IP のみが頼りなので、IPが取れない環境では「PIN単位の失敗回数」を補助キーにするか、上限値を保守的に設定する方針をオーナーに確認。
- **要確認（invite_logs 再利用可否）**: 本チケットは専用テーブル `public_action_logs` を新設する方針（invite_logs はスキーマ非適合）。invite_logs を流用したい場合は `inviter_id`/`invitee_role` 制約の緩和が必要になり invite 側と混在するため非推奨。この方針でよいか最終確認。
- PIN のハッシュ化（平文保存の是正）は本チケット範囲外（`verify-pin` が平文一致前提＝ハッシュ化すると照合方式変更が必要。DESIGN.md でも S3 の主対策は UNIQUE+レート制限に置いている）。ハッシュ化は S1 設計（R12）と併せた別スケジュール判断。
