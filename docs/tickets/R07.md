# R07: Supabaseクライアント軽量化の技術検証（spike）

## 目的
`@supabase/supabase-js` の `createClient` は storage-js(84KB) + realtime-js(73KB) + functions-js(7.5KB)（計約 165KB 圧縮前・バンドルの 10% 強）の未使用サブクライアントを同梱する。本アプリでは `supabase.storage` / `supabase.channel` / `functions.invoke` / realtime の使用が 0 件（DESIGN.md P1-2）。`@supabase/supabase-js` を使わず **auth-js（GoTrueClient）+ postgrest-js を直接組む構成**の実現可否を、スクラッチディレクトリでのプロトタイプ + ビルドサイズ比較で検証し、互換ラッパーの実装コスト見積もりと推奨（やる/やらない）を報告書にまとめる。**本体コードは一切変更しない（調査のみ）。**

## 対象ファイル
- **調査のみ・非変更**: `src/app/lib/supabase.ts`（`createClient` 呼び出し・`auth` オプション設定）、`src/app/lib/adminApi.ts`（`supabase.auth.getSession`/`refreshSession` を Edge Function 呼び出しのトークン取得に使用。Edge Function 呼び出し自体は生 `fetch`）、`src/app/context/AuthContext.tsx` ほか `supabase.*` 使用箇所全般。
- **成果物（新規作成）**: `docs/spike-supabase-slim.md`（報告書）
- **プロトタイプ**: スクラッチディレクトリ（リポジトリ外／使い捨て。本体に混ぜない）

## 実装手順
1. **現行 API 面の棚卸し（コード実測）**
   - `supabase.auth.*` 使用メソッド（`grep` で確定済みの実態）:
     - `getSession` / `refreshSession` / `signInWithPassword` / `signUp` / `signOut` / `onAuthStateChange` / `getUser` / `updateUser` / `verifyOtp` / `setSession` / `exchangeCodeForSession` / `resetPasswordForEmail` / `getSessionFromUrl`（※ `getSessionFromUrl` は supabase-js 2.56 に存在しない誤用＝ S8 の実バグ。R11 で正規 API へ置換予定。ラッパー設計では正規 API 前提で扱う）
   - `supabase.from(table).*` 使用: `select` / `insert` / `update` / `delete`（テーブル: `units` / `categories` / `questions` / `profiles`）。
   - `createClient` の `auth` オプション: `persistSession: true` / `autoRefreshToken: true` / `detectSessionInUrl: true`。
   - **将来増える API**: X03 で `supabase.rpc('import_questions', ...)`（PostgREST RPC）が追加される。互換ラッパーは postgrest-js の `.rpc()` も対象に含める必要がある（見積もりに反映）。
   - storage / realtime / channel / functions.invoke: **使用 0 件**（排除しても機能影響なし）を報告書に明記。
2. **プロトタイプ構築（スクラッチ）**
   - スクラッチディレクトリに最小 Vite（または rollup/esbuild）プロジェクトを 2 つ用意し、同一の最小利用コード（getSession → from('units').select → rpc 呼び出しのモック等）でバンドルサイズを比較する。
     - (A) `@supabase/supabase-js`（`createClient`）版
     - (B) `@supabase/auth-js`（GoTrueClient）+ `@supabase/postgrest-js`（PostgrestClient）直接組み立て版
   - (B) では auth-js に `persistSession`/`autoRefreshToken`/`detectSessionInUrl` 相当のオプション・`storageKey`・`fetch` を渡し、postgrest-js には Supabase REST エンドポイント（`{url}/rest/v1`）と `apikey`/`Authorization` ヘッダ、認証トークン連携（auth の access_token を postgrest ヘッダへ反映する仕組み）を組む。
   - `vite build`（または `esbuild --bundle --minify`）+ gzip でメインチャンクサイズを実測し、(A)/(B) の差分（KB / gzip KB / 削減率）を記録。
3. **互換ラッパーの実装コスト見積もり**
   - 現行 `export const supabase` と同じ表面（`supabase.auth.*` / `supabase.from().*` / `supabase.rpc()`）を保つ薄いラッパーを `supabase.ts` に閉じ込めた場合の変更範囲を評価:
     - auth-js 単体は `createClient` 経由で得られる `GoTrueClient` とほぼ同一 API のため大半はそのまま使える見込み。要確認点として、セッションと PostgREST ヘッダの自動連携（`createClient` が内部で行う `onAuthStateChange` → REST ヘッダ更新）を手動配線する必要がある。
     - `detectSessionInUrl`（メール認証/招待リンクのハッシュ処理）の等価挙動を auth-js オプションで担保できるか（`AcceptInvite`/`ResetPassword` の認証リンク処理に影響）。
     - `apikey` ヘッダ・RLS 前提のトークン付与が全 `from()`/`rpc()` で正しく効くか。
   - 「本体コード（`supabase.ts` 以外）を変更しない薄いラッパーで置換可能か」「移行の破壊リスク（招待/パスワード再設定/RLS）」を段階（S/M/L）で見積もる。
4. **報告書作成（`docs/spike-supabase-slim.md`）**
   - 構成: (1) 使用 API 面の一覧、(2) storage/realtime/functions 未使用の確定、(3) プロトタイプのビルドサイズ実測（表: 現行 vs 直接組み立て、gzip 差）、(4) 互換ラッパー実装コストとリスク、(5) **推奨判断（やる/やらない）と理由**、(6) やる場合の実装アウトライン（別チケット化の粒度）。

## 備考
- `getFunctionsBaseUrl`（`supabase.ts` 19行目）は Edge Function 呼び出し用の URL 生成ヘルパで、`functions-js`（`functions.invoke`）は使っていない（`adminApi.ts` は生 `fetch`）。functions-js が完全に不要である裏付けとして報告書に記載する。
- `getSessionFromUrl`（S8 の誤用 API）は R11 で `setSession`/`exchangeCodeForSession` へ置換予定。ラッパー設計は R11 後の正規 API を前提にすると齟齬が少ない。
- 実装可否の最終判断はオーナー（DESIGN.md / TICKETS.md）。本チケットは推奨提示まで。
- 脆弱性警告 12 件（critical 1 / high 8）は R01 の依存削減後に `npm audit` 再評価（本チケット範囲外だが、サイズ・依存整理の文脈として報告書で言及可）。

## 要確認
