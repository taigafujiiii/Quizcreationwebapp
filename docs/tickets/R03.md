# R03: Context memo化

## 目的
`AuthContext` / `CompanyContext` の Provider `value` が毎レンダー新規オブジェクトとして生成されており（`useMemo`/`useCallback` 未使用）、両 Provider がアプリ全ルートを包むため、`value` の参照変化が全 `useContext` 消費コンポーネントの再レンダー連鎖を引き起こしている（DESIGN.md P1-3）。`value` を `useMemo` 化・関数を `useCallback` 化して不要な再レンダーを解消する。外部から見た挙動（画面・機能・認証フロー・会社選択フロー）は一切変えない。

## 対象ファイル
- `src/app/context/AuthContext.tsx`
  - `value` オブジェクト: 185行目 `<AuthContext.Provider value={{ user, loading, login, logout, register, refreshProfile }}>`
  - 関数定義: `refreshProfile`(72行目) / `login`(151行目) / `logout`(165行目) / `register`(170行目)
- `src/app/context/CompanyContext.tsx`
  - `value` オブジェクト: 46行目 `<CompanyContext.Provider value={{ selectedCompany, selectCompany, clearCompany }}>`
  - 関数定義: `selectCompany`(35行目) / `clearCompany`(40行目)

## 実装手順
1. **AuthContext.tsx**
   - `React` の import に `useCallback`, `useMemo` を追加する（現状 `useEffect, useRef, useState` を使用）。
   - `login` / `logout` / `refreshProfile` を `useCallback` でラップする。
     - `login`(email, password): 依存配列は `[]`（内部で参照するのは `supabase` モジュールと `refreshProfile` のみ）。`refreshProfile` を参照するため依存に `refreshProfile` を含める。
     - `logout`: 依存配列 `[]`（`setUser` は安定）。
     - `refreshProfile`: 91行目で `user`（state）を読むため、依存配列は `[user]`。`refreshRequestIdRef`/`setUser`/`setLoading` は安定なので依存不要。**この `user` クロージャ依存は挙動維持のため必須**（セッション無し時に「現在 user が無ければ null をセット」する分岐）。誤って `[]` にすると古い `user` を掴んで挙動が変わるため注意。
   - `register` の扱い（**重要・順序依存**）:
     - TICKETS.md の順序では R01（死にコード削除, `AuthContext.register()` は S11 の死にコード）が R02→R03 より前段のため、R03 着手時点のベースブランチでは `register` は既にインターフェース(10行目)・`value`(185行目)・実装(170行目)から削除されている想定。その場合は本項目は対象外（`value` に `register` を含めない）。
     - もし着手ブランチに R01 が未反映で `register` が残っている場合のみ、`register` も `useCallback([])` 化して残す（削除は R01 の責務であり R03 では行わない）。
   - `useEffect`(121行目) の依存配列は現状 `[]` のまま変更しない（初期化と `onAuthStateChange` 購読は一度きり。挙動維持）。`refreshProfile` を `useCallback([user])` 化しても、この effect は空依存のまま初回の `refreshProfile` をクロージャで捕捉する現行挙動と同一。
   - `value` を `useMemo(() => ({ user, loading, login, logout, refreshProfile }), [user, loading, login, logout, refreshProfile])` で生成し、Provider に渡す（`register` が残る構成なら `register` も含める）。
2. **CompanyContext.tsx**
   - `React` の import に `useCallback`, `useMemo` を追加する（現状 `useState`）。
   - `selectCompany` を `useCallback((company) => {...}, [])` 化（`setSelectedCompany` と `localStorage` のみ参照、安定）。
   - `clearCompany` を `useCallback(() => {...}, [])` 化。
   - `value` を `useMemo(() => ({ selectedCompany, selectCompany, clearCompany }), [selectedCompany, selectCompany, clearCompany])` で生成し、Provider に渡す。
3. ロジック・分岐・戻り値・localStorage キー・タイムアウト定数などは一切変更しない。純粋に memo 化のみ行う。

## 完了条件
- `npm run typecheck`（R02 で導入した `tsc --noEmit`）がエラーなく完了する。
- `npm run build`（`vite build`）が成功する。
- `AuthContext` / `CompanyContext` それぞれの Provider `value` が `useMemo`、公開関数が `useCallback` でラップされている。
- 外部挙動が不変であること: ログイン/ログアウト/セッション復帰/`is_active=false` 時の自動サインアウト/会社選択・選択解除（localStorage 永続化含む）が従来通り動作する。
- 検証方法: React DevTools Profiler で、`user`/`loading`/`selectedCompany` が変化しない操作（例: 子ルート内の局所的な state 更新）において Auth/Company の consumer が再レンダーされないことを確認（手順は備考）。

## 備考
- **React DevTools Profiler 検証手順**（備考・任意）:
  1. 開発ビルド（`npm run dev`）で管理画面など Context 消費画面を開く。
  2. React DevTools の Profiler タブで記録を開始し、`user`/`loading`/`selectedCompany` を変えない UI 操作（例: フィルタ用ローカル state の変更、ダイアログ開閉）を行う。
  3. 記録を停止し、AuthProvider/CompanyProvider 配下の consumer が「Did not render」または最小限のレンダーになっていることを確認。memo 化前は毎操作で広域再レンダーが観測される。
- `refreshProfile` の `useCallback` 依存に `user` を含めると、`user` 変化時に `value` の identity も変わるが、`user` は元々 `value` に含まれ再レンダー要因であるため挙動・パフォーマンス上の後退はない。memo 化の効果は「`user`/`loading` が不変な大多数の再レンダー」で発揮される。
- ソースコードの実変更は本チケット実装フェーズで行う。本ファイルは仕様のみ。
