# R05: Questions画面最適化

## 目的
問題管理画面（`QuestionsManagement.tsx`）の以下のパフォーマンス課題を解消する（DESIGN.md P2-2 / P2-3 / P2-4）。
- `loadData` の 3 クエリ（units / questions / categories）が直列 `await`（P2-4）→ `Promise.all` で並列化。
- 作成/更新/削除/一括削除の後に `loadData()` で全件（3 テーブル）再取得（P2-3）→ 楽観的ローカル更新（該当行のみ差し替え/追加/削除、失敗時ロールバック + toast）に変更。
- `getCategoryName` / `getUnitNameByCategoryId` がテーブル行ごとに O(n) 線形探索（P2-2）→ `Map` 化（`useMemo`）で O(1) に。

楽観ロック（`updated_at` 一致条件付き update）の既存動作を壊さないこと。外部から見た挙動（画面表示・トースト文言・確認ダイアログ・絞り込み・選択削除）は変えない。

## 対象ファイル
- `src/app/components/admin/QuestionsManagement.tsx`
  - `loadData`: 69〜98行目（直列 await 3 本）
  - `handleSubmit`（作成/更新）: 109〜182行目（末尾 181行目で `loadData()`）
  - `handleDelete`: 217〜229行目（228行目で `loadData()`）
  - `toggleActive`: 236〜267行目（**既に楽観的ローカル更新済み** 262〜266行目。参照実装）
  - `handleBulkDelete`: 324〜338行目（337行目で `loadData()`）
  - `getCategoryName`: 269〜271行目 / `getUnitNameByCategoryId`: 273〜277行目
  - テーブル描画での呼び出し: 680行目（`getUnitNameByCategoryId`）/ 684行目（`getCategoryName`）

## 実装手順
1. **loadData の Promise.all 化**
   - 69〜86行目の 3 つの `await supabase.from(...)` を `const [unitRes, questionRes, categoryRes] = await Promise.all([...])` に置換。各 `select` の列エイリアス・`order` は現状のまま維持。
   - エラー判定（`unitError || questionError || categoryError` 88行目）と `setQuestions`/`setUnits`/`setCategories`（94〜96行目）はそのまま。`questions` の `select` は既に `updatedAt:updated_at` を含む（79行目）ため楽観ロックに必要な `updatedAt` は取得済み。
2. **名前解決の Map 化（useMemo）**
   - `categoryById`（`Map<string, Category>`）と `unitById`（`Map<string, Unit>`）を `useMemo` で構築する（依存: それぞれ `[categories]`, `[units]`）。
   - `getCategoryName(categoryId)` → `categoryById.get(categoryId)?.name || '不明'`。
   - `getUnitNameByCategoryId(categoryId)` → `const c = categoryById.get(categoryId); return c ? (unitById.get(c.unitId)?.name || '不明') : '不明'`。
   - 戻り値・'不明' フォールバックは現状と同一に保つ。
3. **ミューテーション後の楽観的ローカル更新**（`toggleActive` 262〜266 の既存パターンに合わせる）
   - **更新（editingQuestion あり, 126〜154行目）**: update は既に `.select('updatedAt:updated_at')`（142行目）で新 `updatedAt` を返す。成功時、`loadData()`（181行目）を呼ばず、`setQuestions` で該当行のみ差し替える（フォーム値 + `updatedAt: data.updatedAt`）。`AssignmentsManagement.handleSaveEdit`（579〜596行目）が同型の参照実装。
   - **作成（insert, 156〜170行目）**: 現状 insert は `.select()` を持たず戻り値を使っていない。楽観的にローカル追加するため、insert に `.select('id, text, optionA:option_a, optionB:option_b, optionC:option_c, optionD:option_d, correctAnswer:correct_answer, answerMethod:answer_method, explanation, categoryId:category_id, isActive:is_active, isAssignment:is_assignment, updatedAt:updated_at').single()` を付与し、返却行を `setQuestions([created, ...questions])` で先頭に追加する（一覧は `created_at` 降順のため新規は先頭）。**`updatedAt` を必ず取得**（以後の編集/トグルの楽観ロック条件に必要）。クエリ形状は変わるが外部挙動は不変。`AssignmentsManagement.handleCreateAssignment`（474〜504行目）が参照実装。
   - **削除（handleDelete, 217〜229行目）**: 成功時 `loadData()` を呼ばず、`setQuestions(prev => prev.filter(q => q.id !== id))` でローカル削除。楽観的にするなら削除前に `prev` を退避し、`supabase...delete()` が error なら退避値へロールバック + 既存の `toast.error('問題の削除に失敗しました')`。`confirm` ダイアログ・成功トーストは現状維持。
   - **一括削除（handleBulkDelete, 324〜338行目）**: 同様に、成功時 `loadData()` を呼ばず `setQuestions(prev => prev.filter(q => !selectedIds.includes(q.id)))` + `setSelectedIds([])`。失敗時は退避値へロールバック + 既存 toast。件数トースト・`confirm` は維持。
   - **エラー回復パスの `loadData()` は残す**: `updatedAt` 欠落時（122, 240行目）・楽観ロック競合時（151, 258行目）の `await loadData()` は最新状態の取得に必要なため変更しない。
4. **楽観ロック不変性の担保**
   - 更新・トグルの `.eq('updated_at', ...)` 条件、`!data` 時の競合トースト + `loadData()` は現状維持。
   - 楽観的ローカル反映では、update/insert が返す新 `updatedAt` を必ずローカル `Question.updatedAt` に反映し、直後の連続編集でも正しく競合検知できるようにする（`toggleActive` 264行目と同じ方針）。
5. ロジック・トースト文言・絞り込み（`filteredQuestions` 279行目〜, 既に `useMemo`）・選択状態管理は変更しない。
