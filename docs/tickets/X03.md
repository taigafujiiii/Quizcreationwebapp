# X03: インポートRPC(migration)

## 目的

xlsx インポートを **単一トランザクション・全件ロールバック** で実行する Postgres RPC 関数 `import_questions(jsonb)` を新設する。DESIGN.md「要件①」§3 に基づき、既存 CSV インポートの「バッチ途中失敗で中途半端に残る」問題を構造的に解消する。処理は (1)単元名解決/自動作成 (2)カテゴリ名解決/自動作成 (3)ID有り→update / ID無し→insert を1トランザクションで行い、いずれか1行でも失敗すれば全件ロールバックする。**スキーマ変更は関数追加のみ・既存テーブル定義とデータに非破壊**(後方互換)。

## 対象ファイル

- `supabase/migrations/20260722000000_import_questions.sql`(**新規作成**)
- 参考(変更しない): `supabase/migrations/20260206000000_init.sql`(`questions`/`categories`/`units` 定義、`is_admin()`、RLS ポリシー、`set_updated_at` トリガ)
- 参考(変更しない): `supabase/migrations/20260210001000_multi_correct_answer.sql`(`questions_correct_answer_format_check` = `^(?:[ABCD](?:,[ABCD])*)$`)
- 参考(変更しない): `supabase/migrations/20260210003000_answer_method_radio.sql`(`questions_answer_method_check` = `answer_method in ('radio','checkbox')`)
- 参考(変更しない): `supabase/migrations/20260210002000_fix_rls_stack_depth.sql`(`is_admin()` の SECURITY DEFINER 版・`grant execute ... to authenticated`)

## 実装手順

### 入力仕様(X04 と厳密に一致させる)

パラメータ名 `p_rows jsonb`(行オブジェクトの配列)。各要素のキー(すべて X01 のパース+バリデーションで正規化済みの値が渡る前提):

| キー | 型 | 説明 |
|------|----|------|
| `row_number` | number(任意) | 元シートの行番号。エラーメッセージ用。無ければ配列 ordinality を使用 |
| `id` | string(任意) | 問題 UUID。空/未指定=新規、値有り=上書き対象 |
| `unit_name` | string(必須) | 単元名 |
| `category_name` | string(必須) | カテゴリ名 |
| `text` | string(必須) | 問題文 |
| `option_a`〜`option_d` | string(必須) | 選択肢A〜D |
| `correct_answer` | string(必須) | radio=`A` / checkbox=`A,C`(**昇順正規化済み**) |
| `answer_method` | string(必須) | `radio` / `checkbox` |
| `explanation` | string(任意) | 解説(空可) |
| `is_active` | boolean(必須) | 公開フラグ |

戻り値: サマリ jsonb `{"inserted": n, "updated": n, "created_units": n, "created_categories": n}`。

### 関数の要件

1. **シグネチャ**: `create or replace function public.import_questions(p_rows jsonb) returns jsonb`、`language plpgsql`、`security definer`、`set search_path = public`。

2. **admin チェック(必須・関数冒頭)**: SECURITY DEFINER は RLS をバイパスするため、呼び出し元の権限を関数内で明示検証する。既存 `public.is_admin()`(`fix_rls_stack_depth.sql` 版、`auth.uid()` を参照)を利用。

   ```sql
   if not public.is_admin() then
     raise exception 'forbidden: admin only';
   end if;
   ```

   - `is_admin()` は PostgREST が設定する `request.jwt.claims`(`auth.uid()`)を参照するため、SECURITY DEFINER(所有者=postgres)配下でも**呼び出し元ユーザー**で正しく判定される。非 admin(anon 含む)は `auth.uid()` が admin プロフィールに一致せず例外→拒否。

3. **入力の空チェック**: `p_rows` が null または空配列なら `raise exception 'no rows'`(または 0件サマリを返す)。

4. **行ループ**: `for v_elem, v_ord in select value, ordinality from jsonb_array_elements(p_rows) with ordinality loop ... end loop;`。行番号は `coalesce((v_elem->>'row_number')::int, v_ord::int)`。

   各行で以下を順に実行(すべて同一トランザクション):

   a. **単元解決/自動作成**: `unit_name` で `units` を検索。

   ```sql
   select id into v_unit_id from public.units
     where name = v_unit_name order by created_at asc limit 1;
   if v_unit_id is null then
     insert into public.units (name, description)
       values (v_unit_name, 'xlsxインポートで自動作成')
       returning id into v_unit_id;
     v_created_units := v_created_units + 1;
   end if;
   ```

   - `units.name` に UNIQUE 制約が無いため `limit 1`(重複名は最古を採用=既存アプリの first-wins と整合)。
   - 同一トランザクション内で先行行が作成した単元は後続行の select で可視のため、同名単元は1回だけ作成される。

   b. **カテゴリ解決/自動作成**: `(v_unit_id, category_name)` で `categories` を検索。

   ```sql
   select id into v_category_id from public.categories
     where unit_id = v_unit_id and name = v_category_name order by created_at asc limit 1;
   if v_category_id is null then
     insert into public.categories (unit_id, name, description)
       values (v_unit_id, v_category_name, 'xlsxインポートで自動作成')
       returning id into v_category_id;
     v_created_categories := v_created_categories + 1;
   end if;
   ```

   c. **ID有り→UPDATE / ID無し→INSERT**:

   ```sql
   v_id := nullif(trim(coalesce(v_elem->>'id', '')), '');
   if v_id is not null then
     -- 上書き。is_assignment / created_at には触れない(既存値維持)。updated_at はトリガで更新。
     update public.questions set
       text = v_text,
       option_a = v_option_a, option_b = v_option_b,
       option_c = v_option_c, option_d = v_option_d,
       correct_answer = v_correct_answer,
       answer_method = v_answer_method,
       explanation = v_explanation,
       category_id = v_category_id,
       is_active = v_is_active
     where id = v_id::uuid;
     get diagnostics v_affected = row_count;
     if v_affected = 0 then
       raise exception '行 % : 指定IDの問題が見つかりません (%)', v_row_number, v_id;
     end if;
     v_updated := v_updated + 1;
   else
     -- 新規。is_assignment は false 固定(DESIGN §2)。
     insert into public.questions
       (category_id, text, option_a, option_b, option_c, option_d,
        correct_answer, answer_method, explanation, is_active, is_assignment)
     values
       (v_category_id, v_text, v_option_a, v_option_b, v_option_c, v_option_d,
        v_correct_answer, v_answer_method, v_explanation, v_is_active, false);
     v_inserted := v_inserted + 1;
   end if;
   ```

   - **ID有り + DB 不存在** → `raise exception`(行番号+ID付き)→ プロシージャ全体が失敗し**全件ロールバック**(DESIGN §3 の重複判定「ID有り+DB不存在=エラー」)。
   - `v_id::uuid` のキャスト失敗(不正 UUID)も例外→ロールバック(X01/X04 側で UUID 妥当性は担保するが DB 側も安全)。

5. **CHECK 制約との整合**: `correct_answer` は既存 `questions_correct_answer_format_check`(`^(?:[ABCD](?:,[ABCD])*)$`)、`answer_method` は `questions_answer_method_check`(`radio`/`checkbox`)で DB がガードする。**RPC 側で形式の再バリデーションは行わない**(責務は X01/X04 のパース+バリデーションが持つ)。万一 CHECK 違反値が渡ってもトランザクションが失敗し全件ロールバックするため不正データは残らない(構造的安全網)。備考の要確認参照。

6. **戻り値**:

   ```sql
   return jsonb_build_object(
     'inserted', v_inserted,
     'updated', v_updated,
     'created_units', v_created_units,
     'created_categories', v_created_categories
   );
   ```

7. **権限付与**: デフォルトの public 実行権を剥奪し、`authenticated` のみに付与(admin チェックは関数内で実施済みだが、多層防御として anon から呼べないようにする)。

   ```sql
   revoke all on function public.import_questions(jsonb) from public;
   revoke all on function public.import_questions(jsonb) from anon;
   grant execute on function public.import_questions(jsonb) to authenticated;
   ```

8. **べき等なマイグレーション**: `create or replace function` を使用。関数追加のみで `alter table` / `update`(データ変更)/ `drop` を一切含めないこと(既存データ非破壊)。

### RLS 下での動作(手順に含める設計根拠)

- `questions` / `categories` / `units` の RLS は「admin のみ manage 可」(`is_admin()` の with-check)。RPC を SECURITY INVOKER にすると admin 呼び出しでも動くが、(a) 全 upsert を1つの特権トランザクションで完結させ、(b) admin 判定を関数内の1点に集約するため **SECURITY DEFINER + 明示的 `is_admin()` ガード** を採用する。
- SECURITY DEFINER は RLS をバイパスするため、**関数冒頭の `is_admin()` チェックが認可の唯一の砦**。これを外すと anon/一般ユーザーが任意書き込み可能になる(必須・削除禁止)。

## 完了条件

- `supabase/migrations/20260722000000_import_questions.sql` が追加され、`import_questions(jsonb)` 関数を定義している。
- 関数が `security definer` + `set search_path = public` + 冒頭 `is_admin()` ガードを持つ。
- admin 認証で正しい行配列を渡すと、単元/カテゴリの自動作成・新規 insert・ID一致 update が1トランザクションで実行され、`{inserted, updated, created_units, created_categories}` を返す。
- ID有り+DB不存在の行を1件でも含むと**全件ロールバック**(それ以前の insert/自動作成単元・カテゴリも残らない)。
- 非 admin(または anon)呼び出しは例外で拒否される。
- 新規 insert 行は `is_assignment = false`、update 行は `is_assignment` に触れず既存値を維持(更新前後で `is_assignment` が不変)。
- **既存データ非破壊**: マイグレーションは関数の create のみで、既存テーブル定義・既存レコードに変更を加えない(`alter table` / データ `update` を含まない)。
- 既存 CHECK 制約(`correct_answer` 正規表現・`answer_method`)に反する値は反映されずロールバックされる。

## 備考

- **要確認(バリデーション責務分担)**: 本設計は「形式バリデーション(必須項目・正解形式・回答方式・整合)は X01/X04 のパース段階で完結、RPC は構造整合(単元/カテゴリ名解決・ID存在)と DB CHECK 制約に依存」とした(DESIGN §3-4 と整合)。レビューで「RPC 側でも形式を二重検証すべき」との判断が出る場合は、手順5に正解形式・answer_method の明示チェック(不一致で `raise exception`)を追加する。**二重検証の要否をレビューで確定**。
- **要確認(正解正規化の所在)**: RPC は `correct_answer` を無加工で INSERT/UPDATE する(昇順正規化は X01 のパースで実施済みの前提)。もし正規化を DB 側で担保する方針なら、RPC 内で `correct_answer` の分割・ソート・再結合を実装する必要がある。**X01 と重複しないよう所在を一本化する**(推奨: X01 側に集約し RPC は無加工)。
- **要確認(行番号の伝達)**: エラーメッセージの「N行目」を元シート行に一致させるため、X04 が各行オブジェクトに任意キー `row_number`(元シート行番号)を含める設計とした。DESIGN §3 の入力キー列挙には `row_number` は無いが、エラー UX 維持のための付加フィールド(無い場合は配列 ordinality にフォールバック)。**X04 実装時にこのキーを送るか要すり合わせ**。
- **同時実行**: 楽観ロック(`updated_at` 一致条件)は本 RPC の update には付けない。xlsx 一括インポートは「まとめて上書き」が意図であり、他画面の単一レコード編集の競合検知とは目的が異なる(DESIGN の楽観ロック方針は個別編集向け)。必要ならレビューで方針確認。
- **タイムスタンプ命名**: `20260722000000` は既存の 14 桁連番規約(直近 `20260328000001`)に従い本日日付で採番。同日に別マイグレーションを追加する場合は連番末尾で衝突回避。
