# R06: Assignments画面最適化

## 目的
課題管理画面（`AssignmentsManagement.tsx`）と、あわせてカテゴリ管理画面（`CategoriesManagement.tsx`）のパフォーマンス課題を解消する（DESIGN.md P2-1 / P2-2 / P2-3 / P2-4）。
- フィルタ関数 `getFilteredAssignmentQuestions` / `getFilteredExistingQuestions` が非メモ化かつレンダーごとに 2 回ずつ実行（length 判定 + `.map`）（P2-1）→ `useMemo` 化。`totalAssignmentCount`（非メモ化の派生値）も `useMemo` 化。
- `getCategoryName` / `getUnitName` がテーブル行ごとに O(n) 線形探索（P2-2）→ `Map` 化（`useMemo`）。
- `loadData` の 3 クエリ（units / categories / questions）が直列 `await`（P2-4）→ `Promise.all` 化。`CategoriesManagement.tsx` の `loadData`（units / categories 直列）も本チケットで並列化する。
- ミューテーション後のローカル状態管理は楽観的更新を維持（P2-3）。

**既存 CSV インポートの機能仕様は変更禁止**（パフォーマンス以外は現状維持）。外部から見た挙動（画面表示・タブ・絞り込み・トースト文言・CSV 取込結果）は変えない。

## 実装手順
1. **AssignmentsManagement: フィルタ関数の useMemo 化**
   - `getFilteredAssignmentQuestions`（関数）を `useMemo` の派生値 `filteredAssignmentQuestions` に変更。依存: `[questions, categories, selectedUnitId, selectedCategoryId]`。ロジック（`q.isAssignment` + 単元/カテゴリ絞り込み）はそのまま。
   - `getFilteredExistingQuestions` を `useMemo` の派生値 `filteredExistingQuestions` に変更。依存: `[questions, categories, selectedUnitId, selectedCategoryId, filterCategory]`（376行目で `filterCategory` を参照している点に注意）。
   - 呼び出し箇所（1476, 1495, 1571, 1587行目）を関数呼び出し `()` から派生値参照に置換。これによりレンダーごとの二重実行が解消。
   - `totalAssignmentCount`（339行目）を `useMemo(() => questions.filter(q => q.isAssignment).length, [questions])` に変更。
2. **AssignmentsManagement: 名前解決の Map 化**
   - `categoryById`（`Map<string, Category>`, 依存 `[categories]`）と `unitById`（`Map<string, Unit>`, 依存 `[units]`）を `useMemo` で構築。
   - `getCategoryName(categoryId)` → `categoryById.get(categoryId)?.name || '不明'`。
   - `getUnitName(categoryId)` → `const c = categoryById.get(categoryId); return c ? (unitById.get(c.unitId)?.name || '不明') : '不明'`（現状の「category 経由で unit 名」ロジックと同一の結果を維持。387〜390行目参照）。
   - 既存の `unitAssignmentCounts` / `categoryAssignmentCounts` / `categoriesInSelectedUnit` / `totalCategoryAssignmentCount`（295〜336行目）は既に `useMemo` 済み。変更不要。
3. **AssignmentsManagement: loadData の Promise.all 化**
   - 255〜270行目の 3 つの `await supabase.from(...)`（units / categories / questions、各 `updatedAt:updated_at` エイリアス含む）を `Promise.all` で並列化。エラー判定（272行目）と `setUnits`/`setCategories`/`setQuestions`（278〜280行目）は維持。
4. **AssignmentsManagement: ミューテーションの楽観的更新は維持**
   - `handleAddToAssignment`（417〜421）/ `handleRemoveFromAssignment`（451〜455）/ `handleCreateAssignment`（499〜501）/ `handleSaveEdit`（594〜596）は**既に `setQuestions` による楽観的ローカル更新 + 楽観ロック（`updated_at` 条件 + 新 `updatedAt` 反映）済み**。これらは維持し、全件 `loadData()` へ戻さない。
   - `updatedAt` 欠落時（395, 428, 531行目）・競合時（412, 445, 573行目）の回復パス `loadData()` は維持。
   - **CSV インポート後の `loadData()`（974行目）は維持**（一括 insert 後の全件同期。CSV 機能仕様変更禁止のため楽観的差分更新には変えない）。
5. **CategoriesManagement: loadData の Promise.all 化**
   - 68〜76行目の units / categories 直列 await を `Promise.all` に。エラー判定（78行目）と `setUnits`/`setCategories`（84〜85行目）は維持。`filteredCategories` / `unitCategoryCounts`（185〜198行目）は既に `useMemo`、`getUnitName`（180行目）は units 参照の単純 find で行数が小さいため本チケットでは Map 化必須ではない（任意）。
6. ロジック・トースト文言・タブ構成・CSV パーサ/バリデーション/自動作成挙動は一切変更しない。

## 備考
- `AssignmentsManagement` のインタラクティブなミューテーション（課題追加/除外/新規作成/編集）は現行コードで**既に楽観的ローカル更新済み**。本チケットの「楽観的ローカル更新（P2-3）」項目は新規実装ではなく「現状維持 + 検証」が主。誤って `loadData()` 全件再取得へ戻さないこと。
- DESIGN.md P2-3 の「全ミューテーション後に `loadData()` 全件再取得（両画面とも 7 箇所）」という記述は旧実装ベースと推測され、現行コードは Assignments 側で既に楽観化されている。実装は現行コードの実態に合わせる（本チケットの主眼は P2-1 フィルタ memo 化・P2-2 Map 化・P2-4 並列化）。
- CSV インポート内の per-row 直列ループ（`ensureUnitId`/`ensureCategoryId`、DESIGN P3）は本チケット範囲外（P3、かつ機能変更リスク）。
- ソースコードの実変更は本チケット実装フェーズで行う。本ファイルは仕様のみ。
