# R11: 認証リンク処理の実バグ修正（S8・存在しない getSessionFromUrl の置換）

## 目的

`supabase.auth.getSessionFromUrl(...)` は **supabase-js 2.56.0（同梱 @supabase/auth-js 2.71.1）に存在しないAPI**。呼び出すと `TypeError` になり、当該リンク形式でパスワード再設定/招待受諾が失敗する（DESIGN.md S8）。正規APIに置換して信頼性を回復する。

**API存在確認（実施済み）**: `node_modules/@supabase/auth-js/dist/module/GoTrueClient.d.ts` に `getSessionFromUrl` は**存在しない**（grep 0件）。利用可能な正規APIは:
- `exchangeCodeForSession(authCode: string)`（124行, PKCE の `?code=` 用）
- `setSession({ access_token, refresh_token })`（263行, `#access_token=...&refresh_token=...` ハッシュ用）
- `verifyOtp({ type, token_hash })`（`?token_hash=&type=` 用）
- クライアント設定 `detectSessionInUrl: true`（`src/app/lib/supabase.ts` で設定済み）により、SDK が初期化時に URL からセッションを**自動検出・確立**する。

## 対象ファイル

- `src/app/components/auth/ResetPassword.tsx`（28行 = `getSessionFromUrl` 呼び出し）
- `src/app/components/auth/AcceptInvite.tsx`（88行 = `getSessionFromUrl` フォールバック）

## 実装手順

### A. ResetPassword.tsx（28行の else 分岐を置換）

現状（20-43行）は `?code=` があれば `exchangeCodeForSession`、無ければ `getSessionFromUrl`（=バグ）。パスワード再設定リンクの**2形式**双方を明示的に処理する。

```tsx
useEffect(() => {
  const init = async () => {
    try {
      // detectSessionInUrl: true により SDK が既にセッションを確立している場合がある
      const { data: pre } = await supabase.auth.getSession();
      if (pre.session?.user) { setReady(true); return; }

      const url = new URL(window.location.href);
      const code = url.searchParams.get('code');
      const tokenHash = url.searchParams.get('token_hash');
      const type = url.searchParams.get('type');

      // ハッシュ形式（#access_token=...&refresh_token=...）
      const hash = new URLSearchParams(url.hash.startsWith('#') ? url.hash.slice(1) : url.hash);
      const accessToken = hash.get('access_token');
      const refreshToken = hash.get('refresh_token');

      if (code) {
        const { error } = await supabase.auth.exchangeCodeForSession(code);
        if (error) throw error;
      } else if (tokenHash && type) {
        const { error } = await supabase.auth.verifyOtp({ type: type as any, token_hash: tokenHash });
        if (error) throw error;
      } else if (accessToken && refreshToken) {
        const { error } = await supabase.auth.setSession({ access_token: accessToken, refresh_token: refreshToken });
        if (error) throw error;
      }

      const { data } = await supabase.auth.getSession();
      if (!data.session?.user) {
        setError('リンクが無効か、期限切れです。');
        setReady(false);
        return;
      }
      setReady(true);
    } catch (_err) {
      setError('リンクが無効か、期限切れです。');
    }
  };
  void init();
}, []);
```

- **2形式の対応明記**: `?code=`（PKCEクエリ）→ `exchangeCodeForSession` / `#access_token=&refresh_token=`（ハッシュ）→ `setSession`。加えて `?token_hash=&type=recovery`（新しめのメールリンク）→ `verifyOtp` も拾う。
- 冒頭の `getSession()` 事前確認で `detectSessionInUrl` による自動確立との二重処理を回避。

### B. AcceptInvite.tsx（87-90行のフォールバック削除）

`establishSessionFromUrl`（48-90行）は `code` / `token_hash+type` / `access_token+refresh_token` の3分岐を持ち、いずれも該当時に `return` する。57行で3条件いずれも無ければ `throw 'missing_invite_token'`。したがって**87-90行の `getSessionFromUrl` フォールバックは到達不能なデッドコードかつ存在しないAPI呼び出し**。単純に削除する。

```tsx
  // Common invite link style: access_token + refresh_token in the URL fragment
  if (accessToken && refreshToken) {
    const { error } = await supabase.auth.setSession({
      access_token: accessToken,
      refresh_token: refreshToken,
    });
    if (error) throw error;
    return;
  }
  // ← 87-90行の getSessionFromUrl フォールバックを削除（到達不能・非存在API）
};
```

- 3分岐は全形式（PKCEコード / token_hash / ハッシュトークン）を既にカバー済みのため、削除で機能欠落は生じない。

## 備考

- **要確認（重大・ルート未登録）**: `ResetPassword` / `AcceptInvite` は**現在の `App.tsx` に Route 登録が無い**（`App.tsx` の import・Route いずれにも存在せず、`*` キャッチオールで `/` → `/select-company` にリダイレクトされる）。同様に `Register` / `Verify` も未登録。つまり本チケットで getSessionFromUrl を正しく直しても、**現状の本番ルーティングでは `/reset-password` `/accept-invite` に到達できず、パスワード再設定・招待受諾フロー自体が機能しない**。一方で `Forgot.tsx`（`redirectTo:/reset-password`）・招待メール（`server/index.ts:39-41` で `/accept-invite` 固定）・`Login.tsx:180`（`/register` リンク）は当該ルートを前提に送出している。
  - これは DESIGN.md が言及する「Register/Verify等のルート変更」および S11「Verify.tsx（ルート未登録）」に連なる構造的乖離。**R11 の指定スコープ（getSessionFromUrl 置換のみ）にはルート追加が含まれない**ため本チケットでは実装しないが、「パスワード再設定の信頼性回復」を完結させるには `/reset-password` `/accept-invite` の Route 登録（+ `/register`）が別途必要。**このルート整備を R11 に含めるか、別チケット（例 R04 の App.tsx 変更に相乗り or 新規）にするかをオーナーに要確認**。
- `verifyOtp` の `type` は recovery/invite/email 等。ResetPassword では `recovery`、AcceptInvite では `invite`/`signup` を想定（AcceptInvite は既に `verifyOtp({ type, token_hash })` を実装済み・変更不要）。
- `detectSessionInUrl: true`（`supabase.ts`）が有効なため、実際にはハッシュ形式は SDK が自動処理することが多い。冒頭 `getSession()` 事前確認でその成立を検知し、手動処理をスキップする設計にしている（二重処理・`bad_code` エラー回避）。
