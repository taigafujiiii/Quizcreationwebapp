# R08: S2 is_active実効化（RLS is_activeチェック + profiles with-check強化 + 無効化時セッション失効）

## 目的

無効化（`profiles.is_active=false`）を「実効化」する。現状は次の3点で無効化が名目だけになっている（DESIGN.md S2 / S4）。

1. RLS ヘルパ関数 `is_admin()` / `allowed_unit_ids()` が `is_active` を参照しないため、無効化されても RLS 上の権限（admin 権限・履修単元の閲覧）が残る（`fix_rls_stack_depth.sql:4-33`）。
2. `profiles` の UPDATE ポリシーの WITH CHECK が `role` / `allowed_unit_ids` しか凍結しておらず、`is_active` / `company_id` / `email` を本人が書き換え可能（自己復活・自社偽装。`init.sql:131-141`、S4）。
3. 無効化時にセッション（refresh token）を失効させないため、無効化済みユーザーが既存トークンで継続アクセスできる（`server/index.ts:749-800`）。

本チケットは (1)(2) を新規 migration、(3) を Edge Function で対処する。**正規UIフローの挙動は不変**（admin操作・本人のusername変更は従来どおり）。

## 対象ファイル

- 新規 migration: `supabase/migrations/<X03より後のタイムスタンプ>_is_active_rls.sql`（例 `20260730000000_is_active_rls.sql`。**X03（import_questions RPC）および既存 migration すべてより後にソートされる連番**であること。R08→R09 の順に適用されるためR09より前）
- `supabase/functions/server/index.ts`（`POST /admin/users/:id/deactivate` = 749-800行）

## 実装手順

### A. RLSヘルパ関数に is_active チェック追加（migration）

`fix_rls_stack_depth.sql:4-33` の2関数を `create or replace` で再定義し、`is_active=true` 条件を加える。関数の署名・`security definer`・`set search_path=public` は現状維持（単元/カテゴリ/問題の read ポリシーはこの2関数を呼ぶだけなので、関数本体の変更のみで実効化される。ポリシー本体の再作成は不要）。

```sql
create or replace function public.is_admin()
returns boolean
language plpgsql
stable
security definer
set search_path = public
as $$
declare
  r text;
  active boolean;
begin
  select role, is_active into r, active
  from public.profiles
  where id = auth.uid();

  return coalesce(active, false) and r = 'admin';
end;
$$;

create or replace function public.allowed_unit_ids()
returns uuid[]
language sql
stable
security definer
set search_path = public
as $$
  select coalesce(
    (select allowed_unit_ids from public.profiles
      where id = auth.uid() and is_active = true),
    '{}'::uuid[]
  );
$$;

grant execute on function public.is_admin() to authenticated;
grant execute on function public.allowed_unit_ids() to authenticated;
```

### B. profiles UPDATE の WITH CHECK 強化（S4含む・migration・同一ファイル）

`init.sql:131-141` の UPDATE ポリシーを `drop policy if exists ... ; create policy ...` で再作成。本人自己更新時に `is_active` / `company_id` / `email` / `role` / `allowed_unit_ids` を現在のDB値に凍結（username のみ変更可）。admin 分岐（service role ではなく認証済みadminクライアント直叩き時）は `is_admin()`（Aで is_active=true 必須化済み）。

```sql
drop policy if exists "Profiles are updatable by owner or admin" on public.profiles;
create policy "Profiles are updatable by owner or admin" on public.profiles
for update
using (auth.uid() = id or public.is_admin())
with check (
  public.is_admin()
  or (
    auth.uid() = id
    and role          = (select p.role          from public.profiles p where p.id = auth.uid())
    and allowed_unit_ids = (select p.allowed_unit_ids from public.profiles p where p.id = auth.uid())
    and is_active     = (select p.is_active     from public.profiles p where p.id = auth.uid())
    and company_id    is not distinct from (select p.company_id from public.profiles p where p.id = auth.uid())
    and email         = (select p.email         from public.profiles p where p.id = auth.uid())
  )
);
```

- `company_id` は NULL を取りうるため `is not distinct from` を使う（`=` だと NULL 同士が UNKNOWN になり弾かれる）。
- 既存 `role` / `allowed_unit_ids` の凍結は現行踏襲（自己参照サブクエリ）。凍結対象を増やしても構造は同型なので stack-depth 再発リスクは低いが、適用後に「本人のusername変更（AcceptInvite.tsx:250-259 の `profiles.update({username})`）」が成功することを必ず確認する（下記完了条件）。

### C. 無効化時のセッション失効（Edge Function）

`server/index.ts` の `deactivate` エンドポイント（749-800行）のソフト削除分岐（`if (isActive) { ... update is_active=false ... }`、776-786行付近）に、セッション失効処理を追加する。

**重要（API確認結果）**: `adminClient.auth.admin.signOut(jwt, scope)` は **ユーザーのJWTを引数に取る**（実装 `node_modules/@supabase/auth-js/dist/module/GoTrueAdminApi.js:31-40`＝`POST {url}/logout?scope=... { jwt }`）。deactivate エンドポイントは対象ユーザーの**userIdしか持たず、JWTを持たない**ため、指示にあった `adminClient.auth.admin.signOut(userId, 'global')` は**そのままでは動作しない**（userId をJWTとして送るため失敗する）。supabase-js Admin API に「userId 指定でセッション失効する」メソッドは存在しない。

代替として、supabase-js Admin API で userId から実効的にトークンを無効化できる **ban** を用いる（`admin.updateUserById(uid, { ban_duration })` は `AdminUserAttributes.ban_duration` をサポート。`types.d.ts:363`）。ban 中のユーザーは GoTrue 側で access/refresh token が拒否される。

```ts
if (isActive) {
  const { error } = await adminClient
    .from('profiles')
    .update({ is_active: false })
    .eq('id', userId);
  if (error) return c.json({ error: error.message }, 500);

  // セッション失効: ban により既存トークンを無効化する
  const { error: banError } = await adminClient.auth.admin.updateUserById(userId, {
    ban_duration: '876000h', // 実質恒久（約100年）
  });
  if (banError) {
    // 失効に失敗しても is_active=false は成立済み。RLSで即時にデータ遮断されるためログのみ
    console.error('deactivate: failed to revoke sessions', banError.message);
  }

  return c.json({ success: true, action: 'deactivated' as const });
}
```

- **再招待との整合**: 再招待系（`/admin/invite` 543行, `/public/register-request` 285行, `approve` 881行）は再招待前に `admin.deleteUser` で stale ユーザーを削除するため、ban は削除で解除され再招待は成立する。破壊なし。
- ハード削除分岐（789行 `admin.deleteUser`）は元々トークンごと失効するため追加不要。
- クライアント側は `AuthContext.tsx:107-113` が `isActive===false` 検知時に `signOut()` するため、UI再訪時にも即ログアウトされる（既存挙動、変更不要）。

## 完了条件

- migration適用後、無効化済みユーザー（`is_active=false`）が: 単元/カテゴリ/問題を SELECT できない（`allowed_unit_ids()` が `{}` を返す）／管理APIで 403（`is_admin()` が false）。
- 無効化済みユーザー本人が `update profiles set is_active=true where id=self` を直接実行しても WITH CHECK で拒否される。同様に `company_id` / `email` / `role` / `allowed_unit_ids` の自己書き換えが拒否される。
- **既存正常系を壊さない**:
  - admin（`is_active=true`）は従来どおり全単元・全管理操作が可能（`admin.spec.ts` の read-only smoke がgreen）。
  - 本人による username 変更（AcceptInvite 登録完了フロー相当の `profiles.update({username}).eq('id', self)`）が成功する。
  - 管理者による他ユーザー更新（`PATCH /admin/users/:id`）は service role 経由でRLSをバイパスするため影響なし（`admin-api-auth.spec.ts` green）。
- deactivate（1回目=ソフト削除）後、対象ユーザーの既存アクセストークンで `GET /admin/users` 等が失敗する（ban 実効）。2回目=ハード削除は従来どおり。
- **既存データの変更禁止**: migration はポリシー・関数のDDLのみ。既存行の UPDATE を含めない。

## 備考

- `admin.signOut(userId,'global')` が使えない件は上記C参照。**要オーナー/実装判断**: セッション失効の実装方式を (i) ban（本チケット推奨・supabase-jsのみで完結）か (ii) GoTrue admin logout エンドポイントの直叩き（auth-js 2.71.1 は未ラップ・存在/仕様は Auth バージョン依存で未検証）にするか。推奨は (i)。
- ban 方式を採る場合、将来「無効化ユーザーの復元（reactivate）」機能を追加する際は `ban_duration: 'none'` での ban 解除が必要になる点を申し送る（現状は復元フローが存在しないため問題なし）。
- `is_admin()` を `sql` から `plpgsql` に保つ（現行が plpgsql）。`security definer` を外さないこと（RLS再帰=stack depth 回避の要）。
- profiles WITH CHECK に凍結列を増やすため、適用直後に「本人username変更」の回帰を必ず手動/E2Eで確認（AcceptInvite/ResetPassword は現状ルート未登録=下記R11備考のため、SQL直実行での確認が確実）。
